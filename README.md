# 分阶段综述论文工作流

版本：2.1.0。基于用户提供的 Astra 版 SKILL.md 与 stage-templates.md（2.0.0）修订。

本包用于管理综述论文的研究、提纲、分节写作、模拟审稿与版本修订。它不是某个领域的文献库，也不是自动投稿或保证录用的工具。核心约定是：每轮只完成一个获准阶段，写作每轮只完成一个约定单元；交付后等待用户确认。

## 1. 文件结构

```text
staged-review-paper/

├── CHANGELOG.md
├── references/
│   └── stage-templates.md
├── assets/
```

SKILL.md 规定执行逻辑；references 提供各阶段字段与判据；assets 是可复制的空白记录；tests 是测试设计和本次静态检查结果。空白模板与验收用例不是实际研究成果。

## 2. 部署与使用边界

解压并保留目录结构，让主文件能定位 references 和 assets。按实际使用平台的 Skill 加载方式导入本目录；平台和部署位置未指定，本包不提供猜测的安装路径，也不宣称已完成平台兼容性验证。主文件保留原有 agent_created 和 version 字段；若宿主有不同的元数据要求，按其实际要求调整，并记录调整。

如果环境只支持附件阅读而不支持注册 Skill，可明确让助手读取主文件和配套模板，按此流程执行。这是文档驱动使用方式，不等于已安装或已验证触发机制。

本包不自带数据库订阅、浏览器、批量下载、OCR、查重或 Word/PDF 转换程序。需要相关能力时由运行环境提供；不可用时必须披露实际范围，不得假装完成。没有附带可执行脚本。

规则与授权遵循运行环境的指令优先级。批准推进研究不等于批准上传私稿、发邮件、付费或投稿；这些操作仍需环境要求的单独授权。无法获取的全文不默认排除，也不绕过付费墙。

## 3. 开始一个论文项目

1. 建立与通用 Skill 分开的论文项目工作区。
2. 按需复制项目初始化、项目状态和决定日志模板；不要先填写不存在的批准记录。
3. 填写实际主题、核心问题、范围、已有材料与期刊信息，未知项如实保留。
4. 让助手先读取 Skill、状态记录和当前阶段模板，只开展当前获准工作。
5. 每次交付更新状态；用户真正确认后再更新决定日志与下一项授权。

示例启动语句（以下为指令结构，不是实际研究信息）：

```text
请使用 staged-review-paper 工作流。
研究主题：【填写实际主题】
目标期刊：【填写实际期刊；未选刊则说明】
综述类型：【已确认类型；或请先协助确认】
论文语言：【填写】
研究边界与排除内容：【填写】
已有材料：【填写】
请先核对必要信息，只完成 S1，交付后等待我确认。
不要使用预印本，不要把摘要阅读称为全文精读。
```

只要求修改 Skill 时不必提供真实选题。目标期刊未定时，可明确批准先做 S1，将期刊对标与格式要求保持待定。

建议工作区：

```text
paper-project/
├── project-brief.md
├── project-state.yaml
├── decision-log.csv
├── terminology.csv
├── journal-requirements.md
├── search-log.csv
├── literature-matrix.csv
├── claim-evidence.csv
├── review-response.csv
├── sources/
├── outlines/
├── drafts/
├── figures/
└── reviews/
```

只有实际写入成功才称记录已保存；不支持文件持久化时，可在对话交付可复制记录。不要把真实论文资料写回通用模板或不同项目之间混用。

## 4. 八阶段与确认方式

| 阶段 | 工作 | 主要交付 |
| --- | --- | --- |
| S1 | 双语检索、现状与选题评估 | 检索记录、文献清单、相似综述、创新性初判 |
| S2 | 五位代表性研究者与争议 | 人物证据卡、理由、争议及候补 |
| S3 | 获取全文、研读与技术讲解 | 逐篇状态、阅读卡、主张证据、技术比较 |
| S4 | 提纲与实质差异 | O-v1、论点证据映射、图表与前沿建议 |
| S5 | 范文对标与提纲升级 | 核验依据、结构分析、O-v2 |
| S6 | 分节写作、摘要及独立组装 | 章节版本、引用、图表、M-v0.1 |
| S7 | 模拟审稿 | R1/R2 等问题清单、位置与验收条件 |
| S8 | 修订与局部回归 | 新稿、逐条回应、遗留问题 |

原始流程第0条是方法说明，第1—8条对应 S1—S8，第9条是 S7/S8 循环。因此保留八阶段，不另设一个重复阶段。

“确认 S1，继续到 S2”是明确推进；“不错”不是批准。“继续”只有唯一待确认完整成果且无关键缺失时才可明确解释为批准。有限成果须明确接受限制，例如“接受已列明的两篇关键全文缺失，保留局限，批准进入 S4”。

执行状态和完成程度分开：待确认不一定完整；条件性批准不能改写为完整完成。获准下一项动作最多一项，无批准时为 null。重大范围变化需复核下游成果。

## 5. 阅读状态、证据与模板

获取状态：待获取、仅摘要可访问、部分正文、完整正文、不可获取。

阅读状态：未读、仅摘要已读、部分已读、定向研读、全文精读。

每个维度只选一个当前状态，两个维度不混加。全文精读要求完整正文已读、提取完成，并核验影响核心论断的补充材料。已下载、已处理、全文精读完成分别统计。

CSV 模板是只有表头的空文件，不含虚构文献或批准记录。采用 UTF-8（带 BOM），字段用中文表头；含逗号或换行的字段使用正常 CSV 引号规则。真实值未知时用“未提供”“未核实”或“不适用”。YAML 中未知或未授权值用 null，尚无记录的集合用 []。

稳定文献 ID 不随文内引用序号改变；候选可用临时 ID，正式纳入后固定且不复用。主张证据表记录原始来源与位置，不只记录相关文献名称。来源与实际阅读版本均应可追踪，预印本不纳入论证和参考文献。

术语表与期刊要求是项目材料，不是固定知识库。术语变更检查全文一致性；期刊要求注明真实来源和核验日期。正文完成后默认再写摘要。

## 6. 版本与接续

提纲 O-v1、O-v2；章节 S6-03-r1、S6-03-r2；全文 M-v0.1、M-v0.2；审稿 R1、R2。序号不是小数，M-v0.9 后为 M-v0.10。用户确认进入投稿准备后才标候选终稿 M-v1.0。

新会话至少提供项目状态、最新实际产物、最近批准记录和相关证据记录。示例：

```text
请接续本项目，先核对 project-state、decision-log 和最新产物。
不要猜测既往确认，不重走已经核验的阶段。
只执行已批准的下一项工作；信息不一致时先指出并澄清。
```

不要仅凭助手的旧总结认定用户批准了某个版本。旧稿保留，新稿记录父版本、对应审稿轮次、证据变化和遗留问题。

## 7. 测试与本次验证范围

本包提供 15 个行为验收用例和空白测试记录。用例未实际运行，不能称为通过。维护者应在实际平台运行、保存输出、记录偏差，再按结果修订。

本次仅进行了本地静态检查：文件非空、主文件相对引用存在、版本一致、YAML 可解析、CSV 表头有效、关键规则修订到位和 ZIP 完整性。详细结果见 tests/static-check-report.json。

本次没有做真实文献检索、全文精读、端到端论文写作、平台触发验证或实际投稿验证。静态检查通过不代表对话行为或学术内容已验证。

## 8. 后续维护

变更记入 CHANGELOG。调整确认机制、证据状态或文件字段时同步更新主文件、模板、README 和相关测试。先修复已观察到的失败，再考虑增加复杂脚本。

本包未添加第三方查重、投稿上传或自动联系作者功能。它的目标是让每一步研究与修改可检查，不是绕过作者责任或保证录用。
